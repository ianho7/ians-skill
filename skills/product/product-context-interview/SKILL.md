# 把业务未知变成可问的问题

交付临时业务链和首轮提问稿。已确认材料直接复用；未知保留空白，推演与事实分开。只有 HTML 时，页面是业务线索，不能证明现实流程或痛点。

## 沿一次业务追踪交换与交接

选一个有起点和终点的事项，追踪触发、输入、选择与约定、履行、验收及必要的失败补救，按实际业务删减阶段。页面顺序不一定是工作顺序，成功提示也可能早于真实交付。定位原型之外的上游来源、下游接手者和线下处理。

交易可以是劳动、信息或服务的交换，不要求发生支付。对必要参与方写清提供什么、希望得到什么、承担什么；区分使用者、付费者、规则决定者和承担后果的人。每次交接核对输入、接收人、完成凭据与失败后的接手人。

找到阻碍交换的具体原因：找信息、判断质量、协商、履行或追责分别卡在哪里，实际耗费谁的时间、钱、精力或风险。区分服务能力不足与用户无法识别已有能力。对拟议优化检查成本是消除还是转移，谁因此更愿参与、退出或绕过；相关反应作为待验证解释。

异常流程先查规则和处置权限。责任未定、资源不足时，可以建议补规则或协调交接，不把所有问题都归给界面或客服。

## 问知道答案的人

向 leader／规则负责人确认目标、范围、设计由来和可接受的代价；向一线人员还原交付和异常处理；向实际用户询问最近一次经过、绕行和后果。正常做法不清时，先还原通常路径，再追一个重要例外。先了解旧做法，再展示新方案。

将原话、行为和解释分开。用“当时接下来怎么处理”替代暗示麻烦或推荐解法的问法。对方不是信息源时，确认负责人或已有资料。

## 交付与结束

先给一条临时链路，标注节点、交接、各方得失、成本责任及依据／未知；突出最影响理解的断点。首轮合计至多五个主问题，按依赖关系和回答对象排序。

每题写清原型线索、找谁问、可直接说出口的问句、必要时一句中性追问，以及答案改变哪项判断。使用具体业务称呼，合并重复题；不把提纲逐题反问当前使用者。无原型时标为通用起步稿。

获得答案后只更新变化的链路与剩余关键问题。尚未访谈时，交付问题稿即完成，不预先宣布痛点成立或排开发优先级。

依据：《启示录》的机会、用户和原型研究；《俞军产品方法论》的交易、成本与权衡案例。定位见[来源记录](../docs/sources.md)。
