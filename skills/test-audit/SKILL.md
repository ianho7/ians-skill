# Test Audit

Three modes, one value bar.

- **Authoring mode** gates every new or changed test at write time.
- **Audit mode** runs focused sweeps for tests that re-assert source, duplicate stronger proof, couple behavior to implementation, or keep test-only production seams alive.
- **Campaign mode** prunes one whole subsystem's test surface. Before starting a campaign, read [CAMPAIGN.md](CAMPAIGN.md).

Optimize for confidence, not deletion count. Broad audits should be split into coherent follow-up change sets rather than turned into one speculative cleanup.

## Repository contract first

Before applying this skill:

1. Read the repository's applicable instructions and contribution/testing docs, if present. Common examples include `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`, package-level instructions, and CI configuration.
2. Detect the project's actual test runner, package manager/build tool, formatter/linter, type checker, and changed-file or CI gates from repository evidence. Do not assume Vitest, Node.js, a particular directory layout, or a particular default branch.
3. Treat repository-specific commands and policies as authoritative when they conflict with generic examples in this skill.
4. Do not introduce a helper script, production seam, dependency, or test-only API merely to make this skill easier to execute.

## Authoring gate

Before adding any test, answer five questions; a missing answer means do not add it yet:

1. What requirement, user-visible outcome, invariant, or independent contract defines the expected behavior?
   - Derive the expectation independently from the implementation under test. Prefer a requirement, acceptance criterion, public contract, protocol, dependency contract, prior regression, or other external oracle.
   - If the intended behavior is genuinely undocumented, record that uncertainty instead of letting the current implementation silently define "correct."
2. What credible regression makes the test fail?
   - For a bug regression, prefer evidence that the pre-fix or deliberately broken behavior fails for the intended reason and the repaired behavior passes.
3. Why does existing coverage not already catch that failure?
   - Each contract should have one primary test owner at the strongest practical boundary.
   - Another layer needs its own distinct risk, such as transport, serialization, lifecycle, platform, or integration behavior the owner cannot reach.
   - Prefer extending a table-driven/parameterized case or shared fixture over a near-duplicate test.
   - Consolidate duplicated setup in the same change when that consolidation is safe and local.
4. Is the proof independent of the behavior being asserted?
   - Expected values must not be generated by the same helper, parser, formatter, renderer, algorithm, or logic under test.
   - A mock or fake may stand in for an external dependency, but it must not manufacture the very outcome the test claims to prove. When the dependency contract matters, prefer a contract-checked fake or the real dependency at the strongest practical boundary.
5. Does the test require a production seam—export, flag, wrapper, injection hook, getter, reset function, global, or other API—that no production caller needs?
   - If yes, prefer testing at the real owning boundary instead.

Then check the test against every [junk pattern](#junk-patterns). A match fails the gate unless the [retention bar](#retention-bar) identifies an independently meaningful contract it protects.

A test that would fail under behavior-preserving refactoring is likely asserting implementation rather than behavior. Move or rewrite it at the owning boundary before landing it.

Coverage is a discovery signal, not a value target. Uncovered branches can reveal missing failure cases, but do not add tests merely to increase a percentage, line count, or inventory.

Bug regression tests should fail on the pre-fix code for the intended reason and pass after the owner-boundary repair. One regression at the owner boundary normally covers the bug; do not replay the same scenario at every layer it crosses unless each layer owns a distinct failure mode.

## Junk patterns

The shared checklist for authoring and audit modes:

- assertion-free coverage probes;
- self-comparisons and identity copiers;
- copied fixtures, inventories, manifests, snapshots, or export lists with no independent contract;
- exact source, import, AST-shape, or string greps that merely freeze implementation;
- private predicate, helper, or call-shape tests duplicated at real boundaries;
- duplicate invocations of the same contract across layers;
- adapter/provider-local replays of a shared helper's behavior;
- tests whose only purpose is preserving test-only exports, globals, wrappers, flags, getters, or reset hooks;
- dead production code whose only callers are tests;
- expected values produced by the helper, parser, formatter, renderer, or algorithm under test;
- mocks that implement the asserted behavior;
- one identical mock used to stand in for materially different external APIs;
- fixtures that manufacture the receipt, admission, ordering, persistence, or callback evidence that the production owner itself should produce;
- persistence asserted against a store the production path never writes;
- capability tests that restate declared flags instead of exercising the behavior the capability promises;
- negative controls that pass for an unrelated reason;
- rejection/error cases the production path never actually reaches;
- names or fixtures that promise more than the input and assertions exercise;
- tests that exist only to preserve line count, coverage percentage, or an arbitrary inventory when no contract requires it.

## Value bar

Tests justify their maintenance cost by protecting observable behavior, a credible regression, or an independently meaningful contract.

Prefer the strongest practical proof for the contract, not a blanket testing style. Unit, integration, contract, and end-to-end tests are means, not goals; choose the boundary that provides independent evidence with acceptable cost and failure clarity.

In an audit, an existing test that must change for behavior-preserving source reorganization is suspect, not automatically deletable. The authoring gate remains stricter for new tests.

Before judging a candidate, read enough evidence to identify the real owner:

- the complete test, including parameter tables and fixtures;
- the production owner and its public/observable boundary;
- relevant entry points, callers, and callees;
- sibling implementations and overlapping tests;
- CI/test routing;
- relevant repository history when available;
- dependency source, types, or documented behavior when the test claims a dependency-backed contract.

Do not infer ownership from filenames alone.

## Discovery

Keep discovery read-only and report evidence before editing.

For broad scope, derive discovery lanes from the repository's real production-owner boundaries. Typical examples might include:

- core/domain logic;
- adapters/providers/plugins/integrations;
- API/transport/persistence boundaries;
- UI/app layers;
- scripts/tooling/build/release surfaces;
- a cross-cutting pattern sweep.

These are examples, not required directory names.

Outside campaign mode, prefer a few high-confidence candidates over a large speculative inventory. Hunt for the [junk patterns](#junk-patterns).

If parallel or sub-agent execution is available, discovery lanes may run independently. If not, execute the same lanes sequentially without changing the evidence standard.

## Retention bar

Keep a test when it independently enforces a meaningful contract such as:

- public API or SDK behavior;
- protocol or wire format;
- configuration semantics or defaults;
- migration behavior;
- storage/persistence semantics;
- security or authorization properties;
- platform-specific behavior;
- generated or cross-language compatibility;
- package/module boundaries;
- release/build artifacts;
- architecture constraints that cannot be checked more directly at runtime.

Also keep:

- call ordering when order is observable behavior;
- regressions with a credible failure mode;
- source inspection when source text/bytes/paths are themselves the contract and the check survives irrelevant identifier refactors;
- a retained test that fails on the baseline until investigated: treat it as a possible product bug, reproduce it, and repair the owner rather than deleting the test merely to make the suite green.

Static or slow is not itself a deletion reason. A test that resembles implementation detail may still be the cheapest independent guard for a real contract; prove otherwise before removing it.

## Candidate evidence

Record every field below before deleting or consolidating a candidate. A missing field means the candidate is not ready:

- exact test name and location;
- the independent source of expected behavior or contract;
- what failure it can actually detect;
- the production owner/boundary it claims to protect;
- non-test callers of any production or support seam involved;
- stronger remaining owner-boundary proof, or why no proof is needed;
- for mocks/fakes/fixtures that influence the asserted result: what real contract they stand in for and why they do not manufacture the proof;
- relevant history and the reason the test or seam exists, when discoverable;
- production or test-support deletion/simplification unlocked;
- risk;
- focused validation command or procedure.

## Edit shape

Choose one coherent owner-boundary batch.

Prefer to:

- delete obsolete test-only exports, globals, wrappers, flags, getters, resets, and dead production paths rather than preserving compatibility aliases solely for tests;
- move retained regressions to their canonical owners;
- consolidate repeated package/dependency assertions into one owner-level contract;
- preserve distinct risks even when scenarios look superficially similar;
- keep production changes net-negative when the audit reveals test-only seams.

Do not add replacement tests that merely restate the same implementation. Do not turn uncertain candidates into cleanup just to increase deletion counts.

## Validation

Use the repository's own tooling. Do not hard-code a framework or package manager.

1. **Detect commands first.**
   - Read repository instructions, package/build manifests, task files, and CI definitions.
   - Identify the smallest supported command for the affected owner and its sibling/adjacent coverage.
2. **Run focused proof.**
   - Run the smallest relevant owner tests first.
   - For removed source/plan/static assertions, run the executable path, dry-run, build step, or other real contract owner when one exists.
3. **Validate changed files.**
   - Run targeted formatting/linting/type-checking required by repository policy.
   - In Git repositories, run `git diff --check` unless repository policy provides an equivalent.
4. **Run the repository's changed/full gate when justified.**
   - Use an existing changed-file gate if the repository has one.
   - Escalate to broader suites according to repository policy and risk; do not invent a full-suite requirement that the repository does not use.
5. **Inspect the diff.**
   - Separate production/tooling changes from tests and test support.
   - In Git repositories, `git diff --numstat` is a useful input, but report meaning, not just line counts.
6. **Review the final audit change.**
   - Use the repository's required review workflow when present.
   - If an independent review agent/tool is available, use it for a focused preservation review.
   - Otherwise perform a distinct second-pass review against the candidate evidence and retention bar.

Never edit a file while a test/build process is actively generating or rewriting that same file.

## Scope boundary

This skill audits **test value and proof quality**. It may expose design smells, but it does not own a general architecture or changeability review.

When testing a local contract requires broad knowledge of unrelated modules, many collaborator-specific mocks, or fragile cross-module setup:

- record the test smell and prefer the strongest practical owner boundary;
- if the evidence suggests a deeper module-boundary/design problem, report it as a named follow-up;
- do not redesign modules, introduce a new architecture, or expand into a repository-wide modularity audit unless that work is separately requested.

Likewise, test selection, CI queue/runner optimization, and full product acceptance automation are separate concerns. Use them as repository context when relevant, but do not broaden a test-audit change merely to optimize them.

## Landing and continuation

Commit, push, open a PR, merge, or land only when authorized.

Follow the repository's own contribution and review flow. Do not assume a particular script, hosting provider, branch name, or PR workflow.

Keep one coherent owner-boundary change set at a time. Before continuing a broad audit after upstream changes land, refresh from the current baseline/default branch and rerun read-only discovery for the next high-confidence batch.

## Handoff

Report:

- scope and owner boundary;
- root causes and removed low-value categories;
- production-owner simplifications;
- retained false positives and why they remain valuable;
- focused and broader proof actually run;
- production/tooling changes separately from tests/test support;
- review/commit/PR/merge state only if those actions were requested or performed;
- named follow-ups and unresolved uncertainty, including boundary/design smells discovered but intentionally left outside test-audit scope.
